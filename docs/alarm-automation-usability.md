# 设备告警、场景联动与邮件通知易用性方案

状态：待实施。验收任务：第一次使用社区版的人，从「温室温湿度传感器」详情配置高温邮件提醒，能够独立找到触发原因、收件人和发送结果。

## 一次配置的操作路径

1. 打开设备详情 → 告警 → 告警规则 → 新建告警规则。从设备进入时预选本设备，保存前可见设备名称。
2. 输入名称「温室高温告警」，选择「温度」「大于」，填写 35。单位从物模型读取。触发和恢复条件分开显示，编辑已有规则时回显其实际配置。
3. 在同一表单选择通知方式。区分「仅记录告警」「使用租户默认策略」「指定通知策略」。使用默认策略时展示实际解析到的策略；若缺少默认策略，就地提示「尚未设置默认通知策略」并提供有权限的配置入口。实现前核对这三种选择与接口语义，尤其是空值代表什么。
4. 选择已有邮件策略后，就地显示渠道和有权限查看的收件对象。收件人按策略解析，租户登录邮箱不能用来推断实际收件人。已有可用渠道时直接复用；缺少渠道时，按权限给出「配置邮件渠道」或「联系管理员开通邮件渠道」。保存一次即可。
5. 模拟器上报常温，再上报超过阈值的温度。若原告警仍未恢复，先满足该规则实际恢复条件。在「告警历史」打开新记录，核对设备、触发时间和温度，点击「查看通知记录」，再到对应邮箱核对设备名称、触发值及时间。

## 四处局部调整

| 位置 | 页面呈现 | 交互细节 |
| --- | --- | --- |
| 设备 → 告警 → 告警历史 | 第一行显示规则中文名称、级别、未恢复/已恢复。第二行显示时间与读数，例如「最近检测　38.1 °C，阈值 > 35 °C」 | 有触发时证据才显示「触发时」。确认人及确认时间放在详情，确认与恢复分别展示。设备页已有设备名称，告警中心则补上设备名称 |
| 设备 → 告警 → 告警规则 | 现有「告警策略」标签改为「告警规则」。每项显示名称、启停状态、触发条件、通知策略 | 点「编辑规则」打开对应告警编辑页。仅在能核实具体范围时显示「本设备」「来自模板」等。缺少参数时省略该行 |
| 设备 → 自动化 → 场景联动 | 保留现有「如果／那么」编辑方式。首屏列出与设备有关的联动，包含可确定对它生效的模板联动。同一联动只计一次 | 条件选择显示「温度（°C）」等物模型名称。「发送通知」「下发设备指令」沿用已有动作。空列表只显示「暂无场景联动」和「新建场景联动」 |
| 告警详情 → 通知记录 | 按本次告警及触发/恢复事件定位，显示渠道、收件对象、时间和投递结果 | 明确仅记录的事件显示「未配置通知」。启用通知但查无记录时显示「暂无发送记录」。邮件服务确认接收后显示「邮件服务已接收」，失败时显示原因，查询失败提供「重新加载」 |

### 一条告警的呈现示例

> **温室温湿度传感器高温告警**　中级　未恢复  
> 发生时间　2026-11-20 16:22:06  
> 最近检测　温度 38.1 °C，阈值 > 35 °C  
> 查看规则　查看通知记录

规则、设备、操作人优先取当前租户可见的业务名称。历史记录优先使用已有快照；名称不可解析时显示「规则名称不可用」等短文案，避免误报已删除。UUID、规则键和原始证据收到折叠的「技术详情」，供复制排查。时间使用平台当前时区。有告警、有无确认、通知是否发出分别取对应记录。

## 实施边界与顺序

1. **先改显示与入口。** 在 `src/views/device/shared/native-device-alarms.vue` 替换直接展示的 `policy_key` 和 `last_evidence`。复用已有名称、时间、读数格式和国际化资源。沿实际告警编辑入口校验路由，覆盖设备内点击、直接打开和刷新。
2. **再理清列表。** 设备详情和设备模板的 `automate.vue` 都组合了 `EffectiveRules` 与场景联动列表。按规则类型与实际作用范围归类；保留模板继承和绑定关系，避免简单删除整个有效规则组件。`effective-rules.vue` 中的条件来源不能直接翻译为「不限设备」。配置页仅展示会影响当前操作的字段，去掉「已读取 3/3 条」「此响应未提供生效参数」等实现说明。
3. **最后接通通知追踪。** 复用现有策略、渠道和发送记录；按告警实例与事件关联，不能仅凭策略 ID、相近时间或相同收件人认领一封邮件。若现有接口缺少关联键，单列最小接口补充，接通前只提供公共「发送记录」入口。名称批量解析限定当前租户，避免逐行请求。此次范围限于展示、入口及必要查询字段，沿用既有判定、恢复和投递机制。

## 验收

- [ ] 初次使用者从温室设备详情创建「温度 > 35 °C」告警，保存前能指出目标设备和邮件收件对象，全程无需查 ID 或另建联动。
- [ ] 分别验证指定策略、默认策略和仅记录告警。仅记录时产生活动告警；选择邮件时，一次新触发可从告警记录追到对应投递，并在测试邮箱核对实际告警内容。
- [ ] 已确认但仍高温时显示「已确认、未恢复」；满足恢复条件后原记录显示「已恢复」；再次超温产生另一条可独立追踪的记录。
- [ ] 另一设备的「温度 > 80 → 发送通知」联动仍可保存执行；它的邮件不会出现在温室这次告警的通知记录中。
- [ ] 本设备、模板继承、不适用三种规则的列表与计数准确；规则入口点击及直接刷新能打开正确记录。
- [ ] 名称缺失、无权限、数据为空、请求失败和邮件发送失败各有可区分的结果。中文界面首屏无裸 UUID、原始 JSON、英文状态码或常驻说明横幅。

## 设计依据

Grafana 允许在规则中指定通知去向，并提供独立的投递查询。这里借用的是这种任务路径，直接复用 ThingsPanel 已有通知策略。[Grafana 通知配置](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/) · [投递排查](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/manage-contact-points/)

表单帮助只用于影响当前选择的信息，尽量压缩成一句；机制说明、实施方案和测试步骤留在本文档。[GOV.UK 表单提示规范](https://design-system.service.gov.uk/components/text-input/)
